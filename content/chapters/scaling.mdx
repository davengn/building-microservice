## Why this lesson matters

Scaling a microservice system is rarely one move. This lesson encourages measurement, targeted intervention, and awareness of the new tradeoffs each tactic introduces.

- Add capacity where the bottleneck actually exists.
- Data access patterns often dominate service scalability.
- Organizational scaling can be as limiting as runtime capacity.

## Core study path

Read with a bottleneck map. For each scaling option, ask what resource it protects and what new complexity it creates.

- Measure before changing topology.
- Separate throughput problems from latency problems.
- Keep data ownership visible when partitioning or replication changes.

## Practice cues

Take a slow user journey and identify the bottleneck. Then propose one application, one data, and one operational change.

- Define the metric that proves the bottleneck moved.
- Check whether caching makes freshness harder.
- Avoid scaling a service that is waiting on another dependency.
